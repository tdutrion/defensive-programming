ポカヨケ - Poka-yoke

Un mot que l'ingénieur Shigeo Shingo donne en 1960 à une idée toute simple, chez Toyota.

  • Poka (ポカ) : une erreur par inattention
  • Yokeru (よける) : éviter
  • Un poka-yoke : un dispositif qui rend une erreur humaine impossible - ou immédiatement visible

Exemple : la carte SD, qui ne rentre que dans un sens.

Deux familles de poka-yoke

🛡️ Prévention

Rend l'erreur physiquement impossible.

Le connecteur USB-C : réversible.

🚨 Détection

Laisse l'erreur se produire, mais la signale immédiatement.

La voiture et son bip ceinture.

On les retrouve dans le code !

Partie 2

La programmation défensive

…ou : comment dire « non » poliment à ses callers

Une définition, un contrat

La programmation défensive :
anticiper que tout ce qui peut mal se passer, se passera mal...
Et refuser les états invalides par construction.

  • Chaque fonction est un contrat : pré-conditions, post-conditions, invariants
  • Plus on encode ce contrat dans les types, moins il faut le vérifier à l'exécution
  • C'est du poka-yoke, appliqué à une signature de fonction

Exemple de contrat typé

❌ Sans


function divide($a, $b) {
    if (!is_numeric($a)) {
        return null;
    }
    if (!is_numeric($b)) {
        return null;
    }
    if ($b == 0) {
        return null;
    }
    return $a / $b;
}

✅ Avec


function divide(
    float $a,
    float $b,
): float {
    if ($b === 0.0) {
        throw new DivisionByZeroError();
    }
    return $a / $b;
}

Le système de types fait 80 % du travail.

Partie 3

Le système de types

Votre meilleur allié, gratuit, livré avec le langage

declare(strict_types=1);

La ligne la plus rentable de votre fichier.

❌ Sans


function add(int $a, int $b): int {
    return $a + $b;
}

add("5", "10");   // 15 — euh, ok ?
add(true, 1.7);   // 2  — au secours

✅ Avec strict_types


declare(strict_types=1);

add("5", "10");
// TypeError: Argument #1 ($a)
// must be of type int, string given

En haut de chaque fichier. Sans exception.

« Sans exception » : même les interfaces


declare(strict_types=1);
interface ShowRepository { /* … */ }

Mettez-le quand même.

⚠️ Pas infaillible : les callbacks core


declare(strict_types=1);

// intdiv(int $num1, int $num2): int — fonction native de PHP

array_map('intdiv', ['10', '20'], ['3', '4']);
// Aucune erreur. Résultat : [3, 5]

intdiv('10', '3');
// TypeError: Argument #1 ($num1)
// must be of type int, string given

La même fonction native : rejetée en appel direct, mais coercée en silence quand elle passe par array_map.

Même chose pour array_filter, array_reduce, usort… mais pas call_user_func, qui reste strict.

Typer les retours, toujours

❌


public function findShow($slug) {
    // Un Show ? null ? false ?
    // Un array brut de l'API ?
}

✅


public function findShow(
    ShowSlug $slug,
): ?Show {
    // Le contrat est clair :
    // un Show ou null.
}

Le type de retour est de la documentation exécutable.

Union & intersection types

Union (PHP 8.0)

« Plusieurs types possibles », sans mentir.


function formatId(int|string $id): string {
    return (string) $id;
}

Si vous avez A|B|C|D, un Value Object remplace souvent l'union.

Intersection (PHP 8.1)

« Doit implémenter plusieurs interfaces ».


function count(
    Countable&Iterator $items
): int { /* … */ }

Plus précis qu'un type concret. Plus mockable.

DNF types (PHP 8.2)

Disjunctive Normal Form : combinaison d'unions et d'intersections.


function process(
    (Countable&Iterator)|null $items,
): void {
    if ($items === null) {
        return;
    }
    // Ici, $items est garanti Countable ET Iterator
}

À lire littéralement : « (Countable ET Iterator) OU null ».

Le type never (PHP 8.1)

« Cette fonction ne rend jamais la main. »


function panic(string $message): never {
    throw new RuntimeException($message);
}

function processBooking(?Cinema $cinema): void {
    if ($cinema === null) {
        panic('Cinéma introuvable');
    }
    // PHPStan sait qu'ici $cinema n'est pas null
    $cinema->book(/* … */);
}

Génériques (via PHPStan/Psalm)

Pas dans le langage… mais dans les annotations.


/**
 * @template T
 */
final readonly class TypedCollection {
    /** @param list<T> $items */
    public function __construct(private array $items) {}

    /** @return T */
    public function first(): mixed {
        return $this->items[0];
    }
}

/** @var TypedCollection<Showtime> $showtimes */
$showtimes = new TypedCollection($rawShowtimes);
$showtimes->first(); // inféré comme Showtime, pas mixed

PHPStan, Psalm et PhpStorm comprennent parfaitement.

Cas pratique : la réponse qui change de forme

/show/{slug}/showtimes/{cinemaSlug} renvoie un objet daté ou un tableau vide, selon les cas :

❌ Avant


function getShowtimes($show, $cinema) {
    $r = $this->http->get(/* … */);
    if (is_array($r) && count($r) === 0) {
        return [];
    }
    return $r; // object clé=date, ou {}
}
// L'appelant doit deviner la forme.

✅ Après


function getShowtimes(
    ShowSlug $show,
    CinemaSlug $cinema,
): ShowtimeList {
    $r = $this->http->get(/* … */);
    return ShowtimeList::fromApiResponse($r);
}
// Toujours un ShowtimeList. Point.

L'incohérence de l'API s'arrête à la frontière du système.

Ce que ShowtimeList fait vraiment


final readonly class ShowtimeList {
    /** @param list<Showtime> $items */
    private function __construct(private array $items) {}

    public static function fromApiResponse(array|object $raw): self {
        // `[]` (rien de programmé) et `{date: [...]}` convergent ici :
        // (array) [] reste [], le foreach ne fait juste rien.
        $items = [];
        foreach ((array) $raw as $times) {
            foreach ($times as $t) {
                $items[] = Showtime::fromApi($t);
            }
        }
        return new self($items);
    }

    public function nextBookable(): ?Showtime {
        return array_find($this->items, static fn(Showtime $t) => $t->isBookable());
    }
}

Récap

  • ✅ declare(strict_types=1) partout
  • ✅ Tous les paramètres et retours typés
  • ✅ Unions seulement quand sémantiquement justifié
  • ✅ Intersections pour les contrats fins
  • ✅ never pour les sorties anormales
  • ✅ Génériques via PHPDoc quand utile
  • ✅ Normaliser les formes incohérentes à la frontière

Partie 4

Immutabilité

L'art de ne jamais changer d'avis

Pourquoi l'immutabilité ?

  • 🧠 Moins de charge cognitive : si je ne peux pas modifier, je n'ai pas à y penser
  • 🔒 Thread-safe par défaut (utile en Swoole, ReactPHP, fibers…)
  • 🧪 Tests triviaux : pas d'état à reconstruire
  • 🐛 Bugs impossibles : pas de mutation surprise depuis une dépendance

readonly properties (PHP 8.1)


final class Cinema {
    public function __construct(
        public readonly string $slug,
        public readonly string $name,
    ) {}
}

$cinema = new Cinema('cinema-pathe-dijon', 'Pathé Dijon');
$cinema->name = 'Autre chose';
// Error: Cannot modify readonly property Cinema::$name

Plus besoin de getter qui ne fait que renvoyer.

readonly

PHP 8.1
readonly property


class Cinema {
    public function __construct(
        public readonly string $slug,
        public string $name, // oups
    ) {}
}

Facile à oublier en revue de code.

PHP 8.2
readonly class


readonly class Cinema {
    public function __construct(
        public string $slug,
        public string $name,
    ) {}
}

Impossible d'oublier.

Le pattern with*()

Comment « modifier » un objet immuable ? On en crée un nouveau.


readonly class Showtime {
    public function __construct(
        public ScreeningTime $time,
        public BookingStatus $status,
    ) {}

    public function withStatus(BookingStatus $status): self {
        return new self($this->time, $status);
    }
}

Visibilité asymétrique (PHP 8.4)

Mutable en interne, mais immuable depuis l'extérieur.


class CinemaProgramme {
    public private(set) int $next24ShowtimesCount = 0;

    public function refresh(int $count): void {
        $this->next24ShowtimesCount = $count; // OK, en interne
    }
}

$p = new CinemaProgramme();
$p->next24ShowtimesCount = 42;
// Error: visibilité asymétrique
$p->refresh(42); // OK

readonly : jamais modifiable après construction. private(set) : modifiable, mais seulement depuis la classe.

Récap

  • ✅ readonly par défaut sur les Value Objects
  • ✅ readonly class dès PHP 8.2 pour ne rien oublier
  • ✅ Visibilité asymétrique pour les entités d'état contrôlé
  • ✅ Pattern with*() pour les « modifications »
  • ❌ Pas de setter sauvage

Partie 5

Value Objects

Le couteau suisse du domaine

Qu'est-ce qu'un Value Object ?

Un objet défini uniquement par sa valeur.

  • Immuable
  • Égalité par valeur, pas par identité
  • Auto-valide à la construction
  • Encapsule un comportement métier

Exemples : ShowSlug, Coordinates, ScreeningTime...

Primitive obsession — un vrai piège

Deux slugs, deux string. Rien n'empêche de les inverser.

❌


function getShowtimes(
    string $show,
    string $cinema,
): array { /* … */ }

getShowtimes($cinemaSlug, $showSlug); // 🤡
// Compile. Plante en prod.

✅


function getShowtimes(
    ShowSlug $show,
    CinemaSlug $cinema,
): ShowtimeList { /* … */ }

getShowtimes($cinemaSlug, $showSlug);
// TypeError immédiat

Le compilateur refuse l'inversion. Plus de test à écrire pour ça.

Les classes derrière ShowSlug et CinemaSlug


final readonly class ShowSlug {
    public function __construct(public string $value) {
        if (trim($value) === '') {
            throw new InvalidArgumentException('Slug de film vide');
        }
    }
}

final readonly class CinemaSlug {
    public function __construct(public string $value) {
        if (trim($value) === '') {
            throw new InvalidArgumentException('Slug de cinéma vide');
        }
    }
}

Deux classes quasi identiques, volontairement : dupliquer six lignes coûte moins cher qu'une hiérarchie pour deux types qui n'ont aucune raison de partager du code demain.

Exemple concret : Coordinates

L'API renvoie { "x": 47.322, "y": 5.041 } — x est la latitude, y la longitude. Vraiment.


final readonly class Latitude {
    public function __construct(public float $value) {
        if ($value < -90 || $value > 90) {
            throw new OutOfRangeException("Latitude invalide : {$value}");
        }
    }
}

final readonly class Longitude {
    public function __construct(public float $value) {
        if ($value < -180 || $value > 180) {
            throw new OutOfRangeException("Longitude invalide : {$value}");
        }
    }
}

final readonly class Coordinates {
    public function __construct(
        public Latitude $latitude,
        public Longitude $longitude,
    ) {}

    public static function fromApi(array $raw): self {
        // le mapping x→latitude, y→longitude ne vit qu'ici
        return new self(new Latitude($raw['x']), new Longitude($raw['y']));
    }
}

Le nom trompeur de l'API (x/y) ne fuit jamais dans le domaine.

Exemple concret : ScreeningTime

L'API renvoie "2026-08-16 20:10:00" — pas de l'ISO 8601, pas de timezone.


final readonly class ScreeningTime {
    public DateTimeImmutable $value;

    public function __construct(string $raw) {
        $dt = DateTimeImmutable::createFromFormat('Y-m-d H:i:s', $raw);
        $errors = DateTimeImmutable::getLastErrors();
        // createFromFormat() accepte "2026-13-45" par rollover silencieux :
        // seul getLastErrors() détecte ce genre de dépassement.
        if ($dt === false || $errors['warning_count'] > 0 || $errors['error_count'] > 0) {
            throw new InvalidArgumentException("Horaire illisible : {$raw}");
        }
        $this->value = $dt;
    }
}

Le format bizarre de l'API est parsé une seule fois, jamais dispersé dans 15 fichiers.

Enums (PHP 8.1) : BookingStatus

La doc de l'API est honnête : « seul available observé ; d'autres valeurs attendues mais non confirmées ».


enum BookingStatus: string {
    case Available = 'available';
    case SoldOut   = 'sold_out';
    case Cancelled = 'cancelled';

    public function isBookable(): bool {
        return $this === self::Available;
    }
}

BookingStatus::from('available');  // ✅
BookingStatus::from('complet');    // ValueError explicite

Une valeur non prévue ne se glisse plus silencieusement dans le système.

Le domaine ne ment plus


final readonly class Showtime {
    public function __construct(
        public ScreeningTime $time,
        public BookingStatus $status,
    ) {}

    public static function fromApi(array $raw): self {
        return new self(
            new ScreeningTime($raw['time']),
            BookingStatus::from($raw['status']),
        );
    }

    public function isBookable(): bool {
        return $this->status->isBookable();
    }
}

ScreeningTime et BookingStatus assemblés en un seul objet — aucun champ brut de l'API ne survit jusqu'ici.

🤸 Object Calisthenics — Règle n°3

« Wrap all primitives and Strings »

Un primitif qui porte une règle métier (un slug, une latitude, un horaire…) devient une classe.

Tirée des 9 règles de Jeff Bay (ThoughtWorks Anthology, 2008) — un entraînement, pas un dogme.

Le parallèle sportif : une contrainte volontaire qu'on s'impose pour gagner en force structurelle.

Récap

  • ✅ Un type métier par concept
  • ✅ Validation à la construction, jamais ailleurs
  • ✅ Immuable et égalité par valeur
  • ✅ Enums pour les ensembles fermés
  • ❌ string et int nus dans les signatures du domaine

Partie 6

Nullabilité maîtrisée

« The billion dollar mistake » — Tony Hoare, 2009

« The billion dollar mistake », version Pathé

Tony Hoare regrettait d'avoir inventé null en 1965. L'API Pathé a trouvé pire : deux façons de dire « rien ».


// contentRating vaut soit un objet, soit [] — jamais null
if (empty($show['contentRating'])) {
    // ...déclenché par [] ET par un objet vide malformé.
    // Lequel des deux vient de se produire ? Aucune idée.
}

On normalise une fois, à la frontière, vers une seule représentation : ?ContentRating.

Le null qui ne veut rien dire

Extrait, tel quel, de la doc de Zone.zoneId :

« Observé null pour la zone idf, et "FR_FR" pour la zone dijon — signification non déterminée à partir des données seules. »

null n'est pas un design. C'est l'aveu qu'on ne sait pas ce que représente la valeur.

Donnez-lui un vrai type — ou supprimez-le. Ne laissez pas l'ambiguïté fuir dans votre domaine.

Null Object pattern


interface Logger {
    public function log(string $message): void;
}

final class NullLogger implements Logger {
    public function log(string $message): void {
        // ne fait rien, ne pète pas
    }
}

class Service {
    public function __construct(
        private Logger $logger = new NullLogger(),
    ) {}
}

Pas besoin de if ($this->logger !== null) partout. Possible grâce à new in initializers (PHP 8.1).

Distinguez find() de get()

❌ Ambigu


public function findShow(
    ShowSlug $slug,
): ?Show {
    // l'appelant doit gérer null
}

✅ Explicite


public function getShow(
    ShowSlug $slug,
): Show {
    return $this->findShow($slug)
        ?? throw new ShowNotFoundException($slug);
}

find() peut échouer. get() est garanti. L'appelant choisit le bon.

Le template Twig — l'autre null

Twig a le même défaut que PHP avant strict_types : par défaut, une variable ou un attribut inconnu ne plante pas.

❌ Silence


{# faute de frappe sur "time" #}
<p>{{ showtime.tim }}</p>
{# rendu : <p></p> — aucune erreur #}

✅ Fail fast


# config/packages/twig.yaml
twig:
    strict_variables: true


<p>{{ showtime.time.value|date('d/m/Y H:i') }}</p>

strict_variables transforme l'accès inconnu en RuntimeError immédiat — le poka-yoke de Twig, symétrique de PHPStan côté PHP.

strict_variables est un réglage global à toute l'application — l'activer suppose que tous les templates ne reçoivent que des données garanties, jamais des tableaux bruts où une clé peut légitimement manquer.

Récap

  • ✅ Si quelque chose ne peut pas être null, ne le déclarez pas nullable
  • ✅ Une seule représentation canonique de « rien », normalisée à la frontière
  • ✅ Null Object plutôt que ?Logger
  • ✅ strict_variables côté Twig, une fois les templates nourris de VOs
  • ❌ Un null dont personne ne sait ce qu'il signifie

Encapsulation

Tell, don't ask

final par défaut, interface pour dépendre

final


final class PatheApiClient {
    public function __construct(
        private HttpClient $http,
    ) {}
}

L'héritage n'est presque jamais ce que vous voulez.

Mais mockable


interface ShowRepository {
    public function getShow(ShowSlug $s): Show;
}

$mock = $this->createMock(ShowRepository::class);

Mockez les interfaces, pas les classes.

Property hooks (PHP 8.4) 🎉

Le string "348" de l'API, validé au plus près de la donnée.


class Auditorium {
    public int $capacity {
        set(string $raw) {
            if (!ctype_digit($raw)) {
                throw new InvalidArgumentException(
                    "Capacité invalide : {$raw}"
                );
            }
            $this->capacity = (int) $raw;
        }
    }
}

$a = new Auditorium();
$a->capacity = '348'; // le string de l'API, entre ici
echo $a->capacity;    // 348 (int), partout ailleurs

Tell, don't ask & Law of Demeter

❌


if ($showtime->status === 'available'
    && $showtime->reservabilityEnd > now()) {
    $emailer->notify($cinema->theaters[0]
        ->gpsPosition->x);
}

✅


if ($showtime->isBookable()) {
    $emailer->notify($cinema->latitude());
}

Chaque -> traversé, et chaque condition dupliquée, crée un couplage. L'objet doit savoir répondre.

Un vrai contrôleur, tell-don't-ask jusqu'au bout


final class ShowController extends AbstractController {
    public function __construct(private ShowRepository $shows) {}

    #[Route('/films/{slug}')]
    public function __invoke(string $slug): Response {
        try {
            $show = $this->shows->getShow(new ShowSlug($slug));
        } catch (ShowNotFoundException) {
            throw $this->createNotFoundException();
        }

        return $this->render('show/detail.html.twig', [
            'show' => $show,
        ]);
    }
}

Un slug vide ? ShowSlug lève avant même d'atteindre le repository — le contrôleur n'a aucun if à écrire pour ça.

🤸 Object Calisthenics — Règle n°5

« One Dot Per Line »

Une seule flèche -> par expression — le calisthenic qui rend la Law of Demeter mécanique : si vous traversez deux objets, c'est qu'il manque une méthode quelque part.

Tirée des 9 règles de Jeff Bay (ThoughtWorks Anthology, 2008) — même famille que la règle n°3.

La discipline du sportif : un mouvement à la fois, propre — pas de chaîne acrobatique qui masque les efforts intermédiaires.

Récap

  • ✅ final par défaut
  • ✅ Interfaces pour les dépendances
  • ✅ Property hooks pour la validation in-class
  • ✅ Tell, don't ask
  • ❌ Pas de getter/setter automatique, pas de chaîne ->->->

Exceptions et résultats

Échouer avec élégance et précision

⚠️ Le défaut de PHP : exceptions unchecked

On lève une exception pour une pré-condition violée, un état système incohérent, une opération impossible — jamais pour piloter le flow normal.


public function placeBooking(Cart $cart): Booking {
    // ↑ la signature ne dit rien des exceptions possibles :
    //   BotBlockedException, ShowNotFoundException,
    //   NoScreeningAvailableException, …
}
LangageModèleConséquence
Java, SwiftCheckedLe compilo force la déclaration
PHP, JS, Python…UncheckedConvention seulement
Rust, HaskellPas d'exceptionsResult<T, E> obligatoire dans la signature

Parade en PHP : @throws en PHPDoc + les throws rules de PHPStan.

Une hiérarchie, avec un vrai cas

La couche anti-bot de Pathé répond, telle quelle :


{ "error": "Error from IP 2a01:e0a:1229:a700:f9a8:8d45:e86b:f8c8 (ref: 18.6857c817.1785576411.100422a5)" }


abstract class PatheApiException extends RuntimeException {}

final class BotBlockedException extends PatheApiException {
    public function __construct(
        public readonly string $ip,
        public readonly string $ref,
    ) {
        parent::__construct("Bloqué par Akamai (ref: {$ref})");
    }
}

On catche au bon niveau d'abstraction — PatheApiException, ou précisément BotBlockedException.

Le pattern Result

Pour les cas d'erreur attendus (validation d'un slug saisi par un utilisateur, par exemple).


abstract readonly class Result {
    public static function ok(mixed $value): SuccessResult { /* ... */ }
    public static function fail(string $error): FailureResult { /* ... */ }
}

$result = ShowSlug::validate($userInput);
match (true) {
    $result instanceof SuccessResult => $this->search($result->value),
    $result instanceof FailureResult => $this->reportError($result->error),
};

Plus explicite que les exceptions pour les chemins prévus.

#[NoDiscard] (PHP 8.5) 🎉

Le complément parfait du pattern Result — et des with*() immuables.


readonly class Showtime {
    #[NoDiscard("Showtime est immuable, withStatus() retourne une nouvelle instance")]
    public function withStatus(BookingStatus $s): self {
        return new self($this->time, $s);
    }
}

$showtime->withStatus(BookingStatus::SoldOut);
// ⚠️ Warning: the return value should be used

Fini les retours ignorés par inadvertance.

Catch ciblé, re-throw avec contexte


try {
    $raw = $this->client->getRawShowtimes($show, $cinema);
} catch (BotBlockedException $e) {
    throw new ShowtimeFetchFailedException(
        show: $show,
        cinema: $cinema,
        previous: $e,
    );
}

Catchez ce que vous savez traiter. L'exception originale est préservée, le contexte métier est ajouté.

Le service complet


final readonly class NextScreeningFinder {
    public function __construct(private PatheApiClient $client) {}

    public function find(ShowSlug $show, CinemaSlug $cinema): Showtime {
        try {
            $raw = $this->client->getRawShowtimes($show, $cinema);
        } catch (BotBlockedException $e) {
            throw new ShowtimeFetchFailedException($show, $cinema, previous: $e);
        }

        return ShowtimeList::fromApiResponse($raw)->nextBookable()
            ?? throw new NoScreeningAvailableException($show, $cinema);
    }
}

Le catch ciblé du slide précédent, plus un second échec possible — aucun état invalide ne peut plus sortir de cette méthode.

Récap

  • ✅ Exceptions du domaine pour le métier
  • ✅ Hiérarchie pour catcher au bon niveau
  • ✅ Re-throw avec contexte
  • ❌ catch (\Throwable $e) n'importe où
  • ❌ Exception pour le flow normal

Partie 9

Développement agentique

Une détection de plus, jamais une prévention

Où ça se range, dans la hiérarchie

Un agent qui relit votre code avant un commit, c'est un poka-yoke de détection — exactement comme une exception fail-fast.

  • Il tourne après que le code a été écrit, jamais avant
  • Il peut se tromper, rater un cas, halluciner une justification
  • Il ne remplace jamais un TypeError

Rappel de la Partie 1 : la hiérarchie n'est pas neutre. Préférez toujours la prévention.

Un skill ciblé, pas un « relis mon code »

Un agent générique dit « ça a l'air bien ». Un skill avec une instruction précise cherche des patterns :


---
name: typing-guard
description: Repère les paramètres et constantes qui devraient être des types dédiés
---
Avant de proposer un diff, vérifie :
- Deux paramètres adjacents de même type primitif représentant
  des concepts différents → proposer un Value Object par paramètre.
- Un ensemble fermé de constantes, ou une string comparée à une
  liste fixe (in_array, ===) → proposer un enum.
Justifie chaque suggestion par un scénario d'erreur concret.

Exemple : le piège déjà vu en Partie 5


function getShowtimes(string $show, string $cinema): array { /* … */ }
⚠️ $show et $cinema sont deux string adjacents représentant des concepts différents (film vs cinéma). Un appel getShowtimes($cinemaSlug, $showSlug) compile. Plante en prod.
→ Proposition : ShowSlug, CinemaSlug.

Exactement le correctif qu'on a écrit à la main en Partie 5 — sauf que là, personne n'a eu besoin d'y penser.

D'autres patterns détectables

❌ Avant


class OrderStatus {
    public const PENDING  = 'pending';
    public const APPROVED = 'approved';
}

if ($status === OrderStatus::APPROVED) { /* … */ }


if (in_array($status, ['pending', 'approved'], true)) {
    /* … */
}

✅ Après


enum BookingStatus: string {
    case Pending  = 'pending';
    case Approved = 'approved';
}

if ($status === BookingStatus::Approved) { /* … */ }


if (BookingStatus::tryFrom($status) !== null) {
    /* … */
}

Même diagnostic dans les deux cas : un ensemble fermé de valeurs qui ne dit pas son nom. BookingStatus a déjà été construit en Partie 5.

Les limites

  • Non déterministe : deux relectures peuvent donner deux avis différents
  • Faux négatifs possibles sur un pattern qu'il n'a jamais vu
  • Faux positifs : parfois deux string adjacentes sont juste... deux string
  • Ne remplace ni le compilateur, ni PHPStan, ni la revue humaine

Un filet de plus dans la chronologie du coût des bugs — pas un raccourci pour sauter les types.

Récap

  • ✅ Un skill ciblé plutôt qu'une relecture vague
  • ✅ Utile en détection : primitive obsession, constantes fermées, ensembles dupliqués
  • ❌ Jamais un substitut aux types, à PHPStan ou à la revue humaine

Conclusion

Ce qu'il faut retenir

Les commandements du PHP défensif

  1. Poka-yoke ton domaine : rends l'erreur impossible avant de la détecter
  2. declare(strict_types=1) tu écriras
  3. Tout, tu typeras (paramètres, retours, propriétés)
  4. readonly par défaut, mutable par exception
  5. Value Objects pour le domaine, primitifs pour l'infra
  6. Exceptions du domaine, jamais \Exception nu
  7. Normalise les API tierces une fois, à la frontière
  8. L'analyse statique tourne à chaque commit, au niveau le plus strict que le code supporte
