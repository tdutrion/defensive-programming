Partie 1

La programmation défensive

…ou : comment dire « non » poliment à ses callers

Définition

La programmation défensive, c'est :

  • Anticiper que tout ce qui peut mal se passer se passera mal
  • Refuser les états invalides par construction
  • Échouer tôt, fort, et au bon endroit
  • Faire confiance au compilateur, pas aux humains

« Make illegal states unrepresentable. » — Yaron Minsky

Défensif ≠ paranoïaque

❌ Paranoïaque


function divide($a, $b) {
    if (!is_numeric($a)) {
        return null;
    }
    if (!is_numeric($b)) {
        return null;
    }
    if ($b == 0) {
        return null;
    }
    if ($a === null) {
        return null;
    }
    return $a / $b;
}

✅ Défensif


function divide(
    float $a,
    float $b,
): float {
    if ($b === 0.0) {
        throw new DivisionByZeroError();
    }
    return $a / $b;
}

Le système de types fait 80 % du travail.

Le contrat

Chaque fonction est un contrat :

  • Pré-conditions : ce que j'attends de mes arguments
  • Post-conditions : ce que je garantis en retour
  • Invariants : ce qui reste vrai du début à la fin

Plus on encode ce contrat dans les types, moins il faut le vérifier à l'exécution.

Fail fast, fail loud

❌ Silence radio


public function setAge($age): void {
    if ($age < 0) {
        $age = 0; // ¯\_(ツ)_/¯
    }
    $this->age = $age;
}

Bug masqué pendant 3 mois. Bonne chance.

✅ Échec immédiat


public function setAge(int $age): void {
    if ($age < 0) {
        throw new InvalidArgumentException(
            "Âge négatif: {$age}"
        );
    }
    $this->age = $age;
}

Stacktrace claire, dev appelé en 5 minutes.

Partie 2

Le système de types

Votre meilleur allié, gratuit, livré avec le langage

declare(strict_types=1);

La ligne la plus rentable de votre composer.json.

Sans elle, PHP essaie d'être poli :


function add(int $a, int $b): int {
    return $a + $b;
}

add("5", "10");   // 15  — euh, ok ?
add("5abc", 10);  // 15  — euh, vraiment ?
add(true, 1.7);   // 2   — au secours

Avec strict_types=1


declare(strict_types=1);

function add(int $a, int $b): int {
    return $a + $b;
}

add("5", "10");
// TypeError: add(): Argument #1 ($a) must be of type int,
//            string given

À mettre en haut de chaque fichier. Sans exception.

Astuce : configurez votre IDE pour l'ajouter automatiquement.

Typer les retours, toujours

❌


public function find($id) {
    // Que retourne-t-on ?
    // Un User ? null ? false ?
    // Un array ? Une Collection ?
    // Une licorne ?
}

✅


public function find(
    UserId $id,
): ?User {
    // Le contrat est clair :
    // un User ou null.
}

Le type de retour est de la documentation exécutable.

Union types (PHP 8.0)

Pour dire « plusieurs types possibles » sans mentir.


function formatId(int|string $id): string {
    return (string) $id;
}

Utiliser avec parcimonie : si vous avez A|B|C|D|E, vous avez probablement un problème de design.

Souvent, un Value Object remplace une union utilement.

Intersection types (PHP 8.1)

Pour dire « doit implémenter plusieurs interfaces ».


function count(Countable&Iterator $items): int {
    foreach ($items as $item) {
        // $items est itérable ET comptable
    }
    return count($items);
}

Plus précis que de demander un type concret. Plus testable. Plus mockable.

DNF types (PHP 8.2)

Disjunctive Normal Form : combinaison d'unions et d'intersections.


function process(
    (Countable&Iterator)|null $items,
): void {
    if ($items === null) {
        return;
    }
    // Ici, $items est garanti Countable ET Iterator
}

À lire littéralement : « (Countable ET Iterator) OU null ».

Le type never (PHP 8.1)

« Cette fonction ne rend jamais la main. »


function panic(string $message): never {
    throw new RuntimeException($message);
}

function processOrder(?Order $order): void {
    if ($order === null) {
        panic('Order disparu');
    }
    // PHPStan sait qu'ici $order n'est pas null
    $order->process();
}

never ⊂ void : c'est encore plus strict.

void vs never

void

La fonction retourne, mais sans valeur.


function log(string $m): void {
    error_log($m);
    return;
}

never

La fonction ne retourne jamais.


function die(string $m): never {
    throw new Exception($m);
    // ou exit() ;
    // ou boucle infinie
}

Conséquence pratique : l'analyseur statique en tire des conclusions de flow.

Génériques (via PHPStan/Psalm)

Pas dans le langage… mais dans les annotations.


/**
 * @template T of object
 * @param class-string<T> $class
 * @return T
 */
function instantiate(string $class): object {
    return new $class();
}

$user = instantiate(User::class); // inféré comme User

PHPStan, Psalm et PhpStorm comprennent parfaitement.

Cas pratique : avant


class OrderService {
    public function process($order) {
        if (!$order) {
            return false;
        }
        if (!isset($order['items'])) {
            return false;
        }
        if (count($order['items']) === 0) {
            return null; // pourquoi pas false ? mystère.
        }
        // ... 50 lignes ...
        return $result;
    }
}

Combien d'erreurs vous pouvez compter ?

Cas pratique : après


class OrderService {
    public function process(Order $order): ProcessedOrder {
        if ($order->items->isEmpty()) {
            throw new EmptyOrderException($order->id);
        }
        // ... travail réel, pas de garde-fou ...
        return new ProcessedOrder(/* … */);
    }
}

Le compilateur (et PHPStan) vous interdit d'appeler process avec autre chose qu'un Order.

Les contrôles deviennent des affirmations métier, pas des vérifs techniques.

Récap section 2

  • ✅ declare(strict_types=1) partout
  • ✅ Tous les paramètres et retours typés
  • ✅ Unions seulement quand sémantiquement justifié
  • ✅ Intersections pour les contrats fins
  • ✅ never pour les sorties anormales
  • ✅ Génériques via PHPDoc quand utile

Partie 3

Immutabilité

L'art de ne jamais changer d'avis

Pourquoi l'immutabilité ?

  • 🧠 Moins de charge cognitive : si je ne peux pas modifier, je n'ai pas à y penser
  • 🔒 Thread-safe par défaut (utile en Swoole, ReactPHP, fibers…)
  • 🧪 Tests triviaux : pas d'état à reconstruire
  • 🗺️ Code prévisible : un objet construit est un objet final
  • 🐛 Bugs impossibles : pas de mutation surprise depuis une dépendance

Constructor property promotion (PHP 8.0)

Avant


class User {
    private string $name;
    private string $email;

    public function __construct(
        string $name,
        string $email
    ) {
        $this->name = $name;
        $this->email = $email;
    }
}

Après


class User {
    public function __construct(
        private string $name,
        private string $email,
    ) {}
}

Boilerplate divisé par trois.

readonly properties (PHP 8.1)


class User {
    public function __construct(
        public readonly string $name,
        public readonly string $email,
    ) {}
}

$user = new User('Alice', 'alice@example.com');
$user->name = 'Bob';
// Error: Cannot modify readonly property User::$name

Plus besoin de getter qui ne fait que renvoyer.

L'attribut public n'est plus un crime si la propriété est readonly.

Limites de readonly par propriété


class User {
    public function __construct(
        public readonly string $name,
        public string $email, // ← oups, mutable
    ) {}
}

Il faut le déclarer sur chaque propriété.

Facile à oublier en code review.

PHP 8.2 résout ça…

Classes readonly (PHP 8.2)


readonly class Point {
    public function __construct(
        public float $x,
        public float $y,
        public float $z = 0.0,
    ) {}
}

$p = new Point(1.0, 2.0);
$p->x = 5.0; // Error

Toutes les propriétés deviennent readonly.

Et impossible d'oublier — c'est au niveau classe.

Le pattern with*()

Comment « modifier » un objet immuable ? On en crée un nouveau.


readonly class Money {
    public function __construct(
        public int $amount,
        public Currency $currency,
    ) {}

    public function withAmount(int $amount): self {
        return new self($amount, $this->currency);
    }
}

$price = new Money(1000, Currency::EUR);
$double = $price->withAmount($price->amount * 2);

Visibilité asymétrique (PHP 8.4)

Mutable en interne, mais immuable depuis l'extérieur.


class Counter {
    public private(set) int $value = 0;

    public function increment(): void {
        $this->value++; // OK, on est dans la classe
    }
}

$c = new Counter();
echo $c->value;     // 0 — lecture publique
$c->value = 42;     // Error: visibilité asymétrique
$c->increment();    // OK
echo $c->value;     // 1

readonly vs visibilité asymétrique

readonly private(set)
Modifiable après construction ?❌ Jamais✅ Depuis la classe
Visible depuis l'extérieur ?✅ En lecture✅ En lecture
Sérialisable / clonable ?⚠️ Subtil✅
Usage typiqueValue ObjectsEntités d'état contrôlé

Collections immutables


/**
 * @template T
 */
final readonly class ImmutableList {
    /** @var list<T> */
    private array $items;

    /** @param list<T> $items */
    public function __construct(array $items) {
        $this->items = array_values($items);
    }

    /** @param T $item */
    public function add(mixed $item): self {
        return new self([...$this->items, $item]);
    }
}

Pas de $list[] = $x. Toujours un nouveau objet.

Récap section 3

  • ✅ Promoted properties pour réduire le bruit
  • ✅ readonly par défaut sur les Value Objects
  • ✅ readonly class dès PHP 8.2 pour ne rien oublier
  • ✅ Visibilité asymétrique pour les entités d'état contrôlé
  • ✅ Pattern with*() pour les « modifications »
  • ❌ Pas de setter sauvage

Partie 4

Value Objects

Le couteau suisse du domaine

Qu'est-ce qu'un Value Object ?

Un objet défini uniquement par sa valeur.

  • Immuable
  • Égalité par valeur, pas par identité
  • Auto-valide à la construction
  • Sans id propre
  • Encapsule un comportement métier

Exemples : Email, Money, UserId, Coordinate, DateRange…

Primitive obsession

Le pire ennemi du domaine.


function transfer(
    string $fromUserId,
    string $toUserId,
    int $amountInCents,
    string $currency,
    string $reference,
): bool {
    // Bonne chance pour appeler ça sans inversion
}

transfer($currency, $amount, $to, $from, $ref); // 🤡

Tout est string ou int. Le compilateur ne peut rien faire pour vous.

Avec des Value Objects


function transfer(
    UserId $from,
    UserId $to,
    Money $amount,
    TransferReference $reference,
): TransferReceipt {
    // Impossible de se tromper dans l'ordre :
    // chaque type est unique et incompatible.
}

Le compilateur refuse transfer($money, $user, …).

Plus de tests à écrire pour vérifier qu'on n'a pas inversé les paramètres.

Exemple : Email


final readonly class Email {
    public function __construct(public string $value) {
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException(
                "Email invalide: {$value}"
            );
        }
    }

    public function domain(): string {
        return explode('@', $this->value)[1];
    }

    public function equals(self $other): bool {
        return strtolower($this->value) === strtolower($other->value);
    }
}

Si vous avez un Email, il est valide. Point.

Exemple : Money


final readonly class Money {
    public function __construct(
        public int $amountInCents,
        public Currency $currency,
    ) {
        if ($amountInCents < 0) {
            throw new InvalidArgumentException('Montant négatif interdit');
        }
    }

    public function add(self $other): self {
        if ($this->currency !== $other->currency) {
            throw new CurrencyMismatchException();
        }
        return new self(
            $this->amountInCents + $other->amountInCents,
            $this->currency,
        );
    }
}

Pourquoi int et pas float ?


var_dump(0.1 + 0.2);
// float(0.30000000000000004)

Floating point + argent = mauvaise idée.

Toujours stocker en plus petite unité (centimes) en int.

Ou utiliser bcmath / brick/money pour les besoins fins.

Identifiants typés


final readonly class UserId {
    public function __construct(public string $value) {
        if (!Uuid::isValid($value)) {
            throw new InvalidArgumentException("UUID invalide");
        }
    }

    public static function generate(): self {
        return new self(Uuid::v7()->toRfc4122());
    }

    public function equals(self $other): bool {
        return $this->value === $other->value;
    }
}

Impossible de passer un OrderId là où un UserId est attendu.

Enums (PHP 8.1)

L'arme ultime contre les magic strings.


// Avant
class OrderStatus {
    public const PENDING = 'pending';
    public const APPROVED = 'approved';
    public const REJECTED = 'rejected';
}

function process(string $status): void { /* ... */ }
process('apporved'); // Typo silencieuse

Backed enums


enum OrderStatus: string {
    case Pending  = 'pending';
    case Approved = 'approved';
    case Rejected = 'rejected';
}

function process(OrderStatus $status): void { /* ... */ }

process(OrderStatus::Approved);  // ✅
process('approved');             // TypeError
process(OrderStatus::from('approved')); // ✅

Sérialisation transparente, comparaison par identité.

Comportement sur enums


enum OrderStatus: string {
    case Pending  = 'pending';
    case Approved = 'approved';
    case Rejected = 'rejected';

    public function label(): string {
        return match($this) {
            self::Pending  => 'En attente',
            self::Approved => 'Approuvé',
            self::Rejected => 'Rejeté',
        };
    }

    public function isFinal(): bool {
        return $this !== self::Pending;
    }
}

match est exhaustif : ajoutez un case, PHPStan vous prévient.

Récap section 4

  • ✅ Un type métier par concept
  • ✅ Validation à la construction, jamais ailleurs
  • ✅ Immuable et égalité par valeur
  • ✅ Enums pour les ensembles fermés
  • ❌ string et int nus dans les signatures du domaine

Partie 5

Nullabilité maîtrisée

« The billion dollar mistake » — Tony Hoare, 2009

Le problème de null


$user = $repository->find($id);
$name = $user->getName();
// TypeError: Call to a member function getName() on null

null est un état parmi tous les autres.

Mais on l'oublie systématiquement.

L'opérateur nullsafe (PHP 8.0)

Avant


$country = null;
if ($user !== null) {
    $addr = $user->address;
    if ($addr !== null) {
        $country = $addr->country;
    }
}

Après


$country = $user
    ?->address
    ?->country;

Mais attention : ?-> est un pansement, pas un design.

Le piège du nullsafe


$total = $cart?->items?->reduce(...)?->total ?? 0;
//                                          ^^
// Vous masquez 4 cas d'erreur différents.

Trop de ?-> = vous avez un problème d'optionalité dans votre modèle.

Demandez-vous : ces objets devraient-ils être nullables ?

Null Object pattern


interface Logger {
    public function log(string $message): void;
}

final class NullLogger implements Logger {
    public function log(string $message): void {
        // ne fait rien, ne pète pas
    }
}

class Service {
    public function __construct(
        private Logger $logger = new NullLogger(),
    ) {}
}

Pas besoin de if ($this->logger !== null) partout.

Possible grâce à new in initializers (PHP 8.1).

Évitez de retourner null

❌


public function find(
    UserId $id,
): ?User {
    // appelant doit
    // gérer null
}

✅


public function get(
    UserId $id,
): User {
    return $this->find($id)
        ?? throw new UserNotFoundException($id);
}

Distinguez find() (peut échouer) de get() (garanti).

throw comme expression (PHP 8.0)


// Idéal dans les expressions ternaires et null-coalescing
$email = $request->get('email')
    ?? throw new BadRequest('email manquant');

$user = $users[$id]
    ?? throw new UserNotFoundException($id);

$status = $validStatuses[$input]
    ?? throw new InvalidStatusException($input);

Lisible, ciblé, échec immédiat.

Récap section 5

  • ✅ Si quelque chose ne peut pas être null, ne le déclarez pas nullable
  • ✅ Nullsafe avec parcimonie
  • ✅ Null Object plutôt que ?Logger
  • ✅ throw dans les expressions pour fail fast
  • ❌ ?->?->?->?-> est un signal d'alarme

Partie 6

Encapsulation

Tell, don't ask

final par défaut


final class UserService {
    public function __construct(
        private UserRepository $repo,
    ) {}
}

Pourquoi ?

  • L'héritage n'est presque jamais ce que vous voulez
  • Préférez la composition
  • Si quelqu'un étend votre classe, vous ne pouvez plus la refactorer
  • Marquez explicitement les classes conçues pour l'héritage

« Mais on ne peut plus mocker ! »

Mockez les interfaces, pas les classes.


interface UserRepository {
    public function find(UserId $id): ?User;
}

final class DoctrineUserRepository implements UserRepository {
    // implémentation
}

// En test
$mock = $this->createMock(UserRepository::class);

Si une classe n'a pas d'interface, demandez-vous : devrait-elle en avoir une ?

Property hooks (PHP 8.4) 🎉

Validation et transformation au plus près de la donnée.


class User {
    public string $email {
        set(string $value) {
            if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
                throw new InvalidArgumentException("Email invalide");
            }
            $this->email = strtolower($value);
        }
    }
}

$u = new User();
$u->email = 'Alice@Example.com';
echo $u->email; // alice@example.com

Property hooks : computed properties


class Rectangle {
    public function __construct(
        public float $width,
        public float $height,
    ) {}

    public float $area {
        get => $this->width * $this->height;
    }

    public float $perimeter {
        get => 2 * ($this->width + $this->height);
    }
}

echo (new Rectangle(3, 4))->area; // 12

Plus besoin de getArea() qui ne fait que calculer.

Named constructors


final readonly class User {
    private function __construct(
        public UserId $id,
        public Email $email,
        public DateTimeImmutable $createdAt,
    ) {}

    public static function register(Email $email): self {
        return new self(UserId::generate(), $email, new DateTimeImmutable());
    }

    public static function reconstitute(
        UserId $id, Email $email, DateTimeImmutable $createdAt,
    ): self {
        return new self($id, $email, $createdAt);
    }
}

Le __construct privé empêche les états invalides.

Tell, don't ask

❌ Ask


if ($order->getStatus() === 'pending'
    && $order->getTotal() > 0
    && !$order->isPaid()) {

    $order->setStatus('approved');
    $order->setApprovedAt(now());
    $emailer->send($order->getEmail());
}

✅ Tell


$order->approve($emailer);

L'objet sait ce qu'il doit faire.

Les conditions métier vivent dans le domaine, pas dans le service.

Pas de getters publics gratuits


// ❌ Anti-pattern : objet anémique
final class User {
    public function getName(): string { return $this->name; }
    public function setName(string $n): void { $this->name = $n; }
    public function getEmail(): string { return $this->email; }
    public function setEmail(string $e): void { $this->email = $e; }
    public function getAge(): int { return $this->age; }
    public function setAge(int $a): void { $this->age = $a; }
    // ... 30 lignes plus tard ...
}

Un objet « sac de données » est un struct, pas une classe.

Si c'est vraiment un struct, autant utiliser readonly class.

Law of Demeter

Ne parlez qu'à vos amis directs.


// ❌
$user->getCompany()->getAddress()->getCity()->getZip();

// ✅
$user->companyZip(); // l'objet sait répondre

Chaque -> traversé crée un couplage.

Et si getCompany() peut retourner null ? Et si getAddress() aussi ?

Récap section 6

  • ✅ final par défaut
  • ✅ Interfaces pour les dépendances
  • ✅ Property hooks pour la validation in-class
  • ✅ Named constructors pour les cas d'usage
  • ✅ Tell, don't ask
  • ❌ Pas de getter/setter automatique

Partie 7

Exceptions et résultats

Échouer avec élégance et précision

Quand throw ?

  • Pré-condition violée → invariant cassé
  • État système incohérent → bug réel
  • Opération impossible → ressource manquante

Pas pour le flow de contrôle métier normal.

Custom exceptions

❌


throw new \Exception(
    "User not found"
);

Impossible à catcher précisément.

✅


throw new UserNotFoundException(
    $userId
);

Classifiable, typée, avec contexte.

Hiérarchie d'exceptions


namespace App\Domain\Exception;

abstract class DomainException extends \RuntimeException {}

abstract class NotFoundException extends DomainException {}

final class UserNotFoundException extends NotFoundException {
    public function __construct(public readonly UserId $userId) {
        parent::__construct("User not found: {$userId->value}");
    }
}

On peut catcher au bon niveau d'abstraction.

Exceptions du domaine vs techniques

🏛️ Domaine

  • InsufficientFundsException
  • OrderAlreadyApprovedException
  • UserNotActiveException

⚙️ Technique

  • DatabaseConnectionException
  • HttpClientException
  • FileNotFoundException

Le cas technique remonte ; le cas domaine se traduit.

Le pattern Result

Pour les cas d'erreur attendus (validation, par exemple).


abstract readonly class Result {
    public static function ok(mixed $value): SuccessResult { /* ... */ }
    public static function fail(string $error): FailureResult { /* ... */ }
}

$result = $validator->validate($input);
match (true) {
    $result instanceof SuccessResult => $this->process($result->value),
    $result instanceof FailureResult => $this->reportError($result->error),
};

Plus explicite que les exceptions pour les chemins prévus.

#[NoDiscard] (PHP 8.5) 🎉

Le complément parfait du pattern Result.


#[NoDiscard("Le résultat de la validation doit être vérifié")]
function validate(Input $input): Result {
    // ...
}

validate($input);
// Warning: The return value of validate() should be used
//          (NoDiscard: « Le résultat de la validation doit être vérifié »)

$r = validate($input); // ✅ OK

Fini les retours ignorés par inadvertance.

#[NoDiscard] : cas d'usage

  • Fonctions de validation → leur résultat doit être consommé
  • Builders / Fluent API → on s'attend à chaîner ou stocker
  • Objets immuables retournés par with*()
  • Result / Either : pas de retour silencieux

readonly class Money {
    #[NoDiscard("Money est immuable, with*() retourne une nouvelle instance")]
    public function withAmount(int $cents): self {
        return new self($cents, $this->currency);
    }
}

$money->withAmount(1000); // ⚠️ warning

Try/catch ciblé

❌


try {
    // 50 lignes
} catch (\Throwable $e) {
    // soupir.
}

✅


try {
    $this->repo->save($u);
} catch (UniqueConstraintException $e) {
    throw new DuplicateEmailException(
        $u->email,
        previous: $e,
    );
}

Catchez ce que vous savez traiter.

Catch et re-throw avec contexte


try {
    $payment = $gateway->charge($order, $card);
} catch (NetworkException $e) {
    throw new PaymentFailedException(
        orderId: $order->id,
        reason: 'Réseau indisponible',
        previous: $e,
    );
}

L'exception originale est préservée. Le contexte métier est ajouté.

PHPStan / monitoring / logs apprécient.

Partie 8

Nouveautés PHP 8.5

Cherry on top — pipe, NoDiscard, et friends

L'opérateur pipe |> (PHP 8.5)

Composition fonctionnelle, sans variable temporaire.

Avant


$result = strtolower(
    trim(
        str_replace(
            ' ',
            '-',
            $title,
        ),
    ),
);

Après


$result = $title
    |> str_replace(' ', '-', ...)
    |> trim(...)
    |> strtolower(...);

Lecture top-down, dans l'ordre d'exécution.

|> et programmation défensive

Chaque étape est une transformation explicite, sans mutation.


$normalizedEmail = $input
    |> trim(...)
    |> strtolower(...)
    |> fn(string $s): Email => new Email($s);

$slug = $title
    |> mb_strtolower(...)
    |> fn(string $s): string => preg_replace('/[^a-z0-9]+/', '-', $s)
    |> trim(...);

Pas de variable intermédiaire = pas de réassignation accidentelle.

|> + first-class callables

Le combo qui change tout.


final readonly class UserNormalizer {
    public function normalize(string $raw): User {
        return $raw
            |> $this->trim(...)
            |> $this->validateEmail(...)
            |> $this->toUser(...);
    }

    private function trim(string $s): string { return trim($s); }
    private function validateEmail(string $s): Email { return new Email($s); }
    private function toUser(Email $e): User { return User::from($e); }
}

Chaque méthode est petite, pure, testable.

array_first() et array_last() (PHP 8.5)

❌ Avant


$first = reset($items);
// ⚠️ Modifie le pointeur interne !
// ⚠️ false si tableau vide
// ⚠️ Pas pur

$first = $items[array_key_first($items)] ?? null;
// Verbeux

✅ Après


$first = array_first($items);
// null si vide
// Ne mute rien

$last = array_last($items);
// pareil, propre

Fonctions pures, sans effet de bord. Comme on les aime.

Gestionnaires d'erreurs accessibles (PHP 8.5)

get_error_handler() et get_exception_handler() existent enfin.


// Avant PHP 8.5 : on devait passer par un workaround crasseux
$previous = set_error_handler(null);
set_error_handler($previous);

// PHP 8.5
$current = get_error_handler();
if ($current !== null) {
    // on peut introspecter, logger, chaîner proprement
}

Utile pour les libs qui veulent composer avec un handler existant sans l'écraser.

Stack traces pour erreurs fatales (PHP 8.5)

Plus de « Out of memory » sans contexte.


Fatal error: Allowed memory size of 134217728 bytes exhausted
  Stack trace:
  #0 /app/src/Service/HugeLoader.php(42): array_merge(...)
  #1 /app/src/Controller/IndexController.php(18): HugeLoader->load()
  #2 /app/public/index.php(7): IndexController->index()
  #3 {main}

Activé par défaut. Plus de debug à l'aveugle.

Constantes finales (PHP 8.5)

Empêcher la surcharge des constantes en sous-classe.


class Base {
    final public const string VERSION = '1.0';
}

class Sub extends Base {
    public const string VERSION = '2.0';
    // Fatal error: Sub::VERSION cannot override final constant Base::VERSION
}

Le contrat d'une constante héritée est protégé.

Combine bien avec PHP 8.3 (constantes typées).

Partie 11

Mise en pratique

Refactoring intégral d'un cas réel

Le code de départ


class UserService {
    public function register($data) {
        if (empty($data['email'])) return false;
        if (empty($data['password'])) return false;
        if (strlen($data['password']) < 8) return false;
        if (!filter_var($data['email'], FILTER_VALIDATE_EMAIL)) return false;

        $user = $this->repo->findByEmail($data['email']);
        if ($user) return null;

        $user = new User();
        $user->email = $data['email'];
        $user->password = password_hash($data['password'], PASSWORD_DEFAULT);
        $user->created_at = date('Y-m-d H:i:s');
        $this->repo->save($user);

        return $user->id;
    }
}

Combien de problèmes ?

Les problèmes

  1. Paramètre $data non typé
  2. Retour ambigu (false | null | int)
  3. Validation impérative dispersée
  4. Mutation directe des propriétés
  5. Date sous forme de string
  6. Pas d'exception : le caller doit deviner
  7. Pas de Value Object : email, password primitifs
  8. Pas de différence entre erreur métier et erreur technique

Étape 1 : Value Objects


final readonly class Email {
    public function __construct(public string $value) {
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidEmailException($value);
        }
    }
}

final readonly class PlainPassword {
    public function __construct(public string $value) {
        if (strlen($value) < 8) {
            throw new WeakPasswordException();
        }
    }
}

Étape 2 : Command typée


final readonly class RegisterUserCommand {
    public function __construct(
        public Email $email,
        public PlainPassword $password,
    ) {}
}

Le contrat d'entrée est impossible à mal construire.

Étape 3 : Entité
(état d'agrégat)


final class User {
    public function __construct(
        public readonly UserId $id,
        public readonly Email $email,
        public HashedPassword $password,
        public readonly DateTimeImmutable $createdAt,
    ) {}

    public static function register(
        Email $email,
        PlainPassword $password,
        Hasher $hasher,
    ): self {
        return new self(
            UserId::generate(),
            $email,
            $hasher->hash($password),
            new DateTimeImmutable(),
        );
    }
}

Étape 4 : Service final


final readonly class RegisterUserHandler {
    public function __construct(
        private UserRepository $users,
        private Hasher $hasher,
    ) {}

    public function __invoke(RegisterUserCommand $command): UserId {
        if ($this->users->existsByEmail($command->email)) {
            throw new EmailAlreadyRegisteredException($command->email);
        }

        $user = User::register($command->email, $command->password, $this->hasher);
        $this->users->save($user);

        return $user->id;
    }
}

Conclusion

Ce qu'il faut retenir

Les 8 commandements du PHP défensif

  1. declare(strict_types=1) tu écriras
  2. Tout, tu typeras (paramètres, retours, propriétés)
  3. readonly par défaut, mutable par exception
  4. Value Objects pour le domaine, primitifs pour l'infra
  5. Exceptions du domaine, jamais \Exception nu
  6. #[NoDiscard] sur les retours qui doivent l'être
  7. PHPStan niveau 9 ou rien
  8. final par défaut, abstrait par intention

Ce qu'on n'a pas pu couvrir

  • Attributs (PHP 8.0) en profondeur — métadonnée et runtime
  • Fibers (PHP 8.1) et programmation asynchrone
  • Lazy objects (PHP 8.4) pour la performance
  • DDD tactique (agrégats, événements, sagas)
  • CQRS / Event Sourcing
  • Type-level programming avec Psalm
  • Property hooks avancés et lazy proxies
